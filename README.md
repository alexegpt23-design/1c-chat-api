# 1C Chat API

Локальный Node.js + Express сервис для поиска справочников, предпросмотра и создания проведённого счёта через 1С Fresh OData. Один счёт содержит одну товарную строку. Номер назначает 1С.

## Запуск

Зависимости уже установлены. Используются существующие `ONEC_URL`, `ONEC_USER`, `ONEC_PASSWORD` из `.env`. Шаблон настроек — `.env.example`; существующий `.env` не нужно заменять.

```powershell
cd C:\1c-chat-api
npm.cmd start
```

По умолчанию сервис слушает `http://127.0.0.1:3001`. `PORT` и `HOST` настраиваются в `.env`. Соединение с 1С прямое; `ONEC_USE_PROXY=true` включает прокси из переменных HTTP(S)_PROXY. Пароли и конфигурация авторизации не выводятся в логи.

## Маршруты

| Метод и путь | JSON запроса | Результат |
| --- | --- | --- |
| `GET /ping` | — | `{ "ok": true, "message": "1С доступна" }` |
| `POST /find-client` | `{ "name": "Торговые решения" }` | Массив `{ ref, name, inn }` |
| `POST /find-product` | `{ "name": "Фискальный накопитель" }` | Массив `{ ref, name }` |
| `POST /find-contract` | `{ "clientRef": "GUID", "name": "Основной" }` | Массив договоров; достаточно одного из полей |
| `POST /preview-invoice` | См. пример ниже | Клиент, договор, товар, количество, цена, НДС и итог; документ не создаётся |
| `POST /create-invoice` | Тот же формат | HTTP 201, `{ number, date, amount, Ref_Key, posted, status }` |
| `POST /test-create-invoice` | `{ "dryRun": false }` или `{}` | Один реальный тестовый счёт; `{ Number, Date, Сумма, Posted, Ref_Key }` |
| `POST /invoice-preview-from-text` | `{ "text": "Выставь счёт…" }` | Найденные реквизиты, цена, НДС и итог без записи |
| `POST /invoice-create-from-text` | Тот же текст, при необходимости выбранные ссылки | HTTP 201, `{ Number, Date, Сумма, Posted, Ref_Key }` |
| `POST /invoice-confirmation-preview` | Текст и при необходимости выбранные ссылки | Предпросмотр, `confirmationId` и `expiresAt`; без записи в 1С |
| `POST /invoice-confirm` | `{ "confirmationId": "…" }` | Создание и проведение подтверждённого счёта; повтор возвращает сохранённый результат |

Поиск исключает группы и помеченные на удаление элементы. Используются исходный, верхний и нижний регистр поисковой строки, апострофы экранируются. Результаты читаются страницами. При отсутствии совпадений поиск возвращает `[]`.

Для счёта нужно однозначное совпадение. При нескольких совпадениях возвращается HTTP 409 с `details.candidates`; повторите запрос с выбранным `clientRef`, `contractRef` или `productRef`. Автоматически выбираются только открытые договоры вида `СПокупателем`, принадлежащие выбранному клиенту. `/find-contract` показывает также договоры поставщика для просмотра.

## Предпросмотр и создание

`examples/invoice.json` содержит данные контрагента, договора и товара из ранее созданного счёта ИНБП-000855:

```json
{
  "clientName": "Торговые решения",
  "contractRef": "c2f2a205-c0d4-4d82-afee-9edf26509515",
  "productRef": "f0d18455-90cc-11ed-80f8-00155d011306",
  "quantity": 1,
  "price": 12200,
  "vatRate": 22,
  "priceIncludesVat": true
}
```

Вместо ссылок можно передать `clientName`, `contractName`, `productName`. Договор можно не указывать, если у клиента ровно один подходящий договор. Ссылки имеют приоритет перед названиями.

`quantity` — положительное число до трёх знаков после точки. `price` — неотрицательная цена до двух знаков. Цена задаётся в запросе, поиск прайс-листов не выполняется. `vatRate` обязателен, если не настроен `ONEC_VAT_RATE`: `БезНДС`, 0, 5, 7, 10, 18, 20, 22; принимается также строка вида `НДС22`. Ставку задаёт вызывающая сторона. `БезНДС` и 0 различаются в документе.

`priceIncludesVat` по умолчанию `true`: НДС выделяется из суммы. При `false` он прибавляется сверху. Денежные расчёты выполняются в целых копейках с округлением половины вверх. В примере итог 12 200, НДС 2 200, сумма без НДС 10 000.

Организация и валюта берутся из договора. Дополнительные поля: `organizationRef` (должна совпадать с договором), `warehouseRef`, `responsibleRef`, `bankAccountRef` (поле 1С `СтруктурнаяЕдиница_Key`), `comment` (до 250 символов). Для ссылок доступны значения по умолчанию в `.env.example`. Для валютного договора требуется явный `exchangeRate`; `exchangeMultiplicity` по умолчанию 1.

`date` необязателен, формат `2026-09-12T15:00:00` без часового пояса, по времени базы. По умолчанию берётся текущее время `Europe/Moscow` (`ONEC_TIMEZONE`). `Number`/`number` во входе отклоняются.

Проверка из второго окна PowerShell, пока сервер запущен:

```powershell
Invoke-RestMethod http://127.0.0.1:3001/ping

$body = [System.Text.Encoding]::UTF8.GetBytes('{"name":"Торговые решения"}')
Invoke-RestMethod http://127.0.0.1:3001/find-client -Method Post -ContentType 'application/json; charset=utf-8' -Body $body

$invoice = [System.IO.File]::ReadAllBytes('C:\1c-chat-api\examples\invoice.json')
Invoke-RestMethod http://127.0.0.1:3001/preview-invoice -Method Post -ContentType 'application/json; charset=utf-8' -Body $invoice
```

Следующий запрос действительно создаёт и проводит новый счёт с данными из файла:

```powershell
Invoke-RestMethod http://127.0.0.1:3001/create-invoice -Method Post -ContentType 'application/json; charset=utf-8' -Body $invoice
```

Для `/create-invoice` и `/test-create-invoice` параметр `dryRun` по умолчанию равен `false`. Явный `dryRun: true` возвращает предпросмотр с HTTP 200 и не выполняет запись в 1С.

## Счёт из текста

Разбор выполняется локально по явным правилам, без внешней AI-модели. Поддерживается один клиент и один товар. Можно использовать предложения, список через запятые или одну строку вида «Счёт для … на … за …». Десятичные точки и запятые внутри чисел сохраняются.

```json
{
  "text": "Выставь счёт ООО Торговые решения. Фискальный накопитель на 15 месяцев. Цена 12200. НДС 22"
}
```

Команда может начинаться с «Выставь счёт», «Создай счет», «Сформируй счёт» или с явного поля «Клиент: …» / «Контрагент: …». Следующее предложение — товар; допускается «Товар: …» / «Номенклатура: …». Цена и НДС обязательны. Необязательные предложения: «Количество 2», «Договор: Основной договор». Без количества используется 1. Принимаются десятичные числа с точкой или запятой и цена вида «12 200,50 руб».

Также поддерживаются все следующие варианты:

```text
Выставь счёт ООО ГИПЕР. Фискальный накопитель на 15 месяцев. Цена 12200. НДС 22
Счёт для ООО ГИПЕР на Фискальный накопитель на 15 месяцев за 12200 рублей НДС 22
ООО ГИПЕР, ФН 15 месяцев, 12200, НДС 22
ГИПЕР ООО, ФН 15 месяцев, 12200 рублей, 22%
Счёт для ООО ГИПЕР на ФН 15 месяцев за 12200 ставка 22
```

Цена извлекается из «Цена 12200», «за 12200», «12200 рублей» или отдельного числового поля списка. НДС извлекается из «НДС 22», «22%», «ставка 22». Числа в названии товара (15 месяцев, ФН-1.2) не используются как цена. Поиск контрагента выполняется через `Catalog_Контрагенты`, товара — через `catalog-service`. Если «ФН 15 месяцев» не найдено, выполняется дополнительный поиск «Фискальный накопитель на 15 месяцев». При нескольких совпадениях по-прежнему требуется выбор ссылки.

Если в тексте отсутствуют необходимые сведения, HTTP 400 содержит их понятные названия и массив `details.missing` (например, `["price"]`). Корректно разобранное название, отсутствующее в справочнике, возвращает HTTP 404; неоднозначный поиск — HTTP 409. Это отличается от ошибки разбора текста.

По умолчанию НДС включён в цену. «НДС 22 сверху» добавляет его к цене; «Без НДС» задаёт освобождение от НДС. Нулевой НДС отличается от «Без НДС». Неизвестные условия, повторные цены и неполный запрос отклоняются HTTP 400 до обращения к справочникам. Положение ООО/ИП в начале или конце названия клиента не мешает поиску.

Если клиент, товар или подходящий договор не найдены, возвращается HTTP 404 без создания документа. При нескольких совпадениях оба endpoint возвращают HTTP 409 с `details.field` и `details.candidates`. Передайте тот же `text` и выбранную ссылку в поле `clientRef`, `productRef` или `contractRef`. Ссылка должна входить в результаты поиска; произвольная ссылка отклоняется HTTP 422. Договоры отбираются только открытые, вида `СПокупателем`, выбранного клиента; сервис создания повторно проверяет реквизиты перед записью.

У «ТОРГОВЫЕ РЕШЕНИЯ ООО» два договора покупателя. Поэтому пример без договора возвращает варианты, а для завершённого preview и боевого теста используется файл `examples/invoice-from-text.json` с выбранным договором из предыдущих тестов:

```powershell
$textInvoice = [System.IO.File]::ReadAllBytes('C:\1c-chat-api\examples\invoice-from-text.json')
Invoke-RestMethod http://127.0.0.1:3001/invoice-preview-from-text -Method Post -ContentType 'application/json; charset=utf-8' -Body $textInvoice

# Создаёт ещё один настоящий счёт:
Invoke-RestMethod http://127.0.0.1:3001/invoice-create-from-text -Method Post -ContentType 'application/json; charset=utf-8' -Body $textInvoice
```

Текстовые endpoint используют существующие сервисы поиска, расчёта, создания и проведения. `/invoice-preview-from-text` всегда только читает данные. `/invoice-create-from-text` поддерживает `dryRun: true` для проверки без записи; по умолчанию `false`. Повторный вызов создания с `false` создаёт новый счёт, поэтому после ошибки записи сначала проверяйте 1С по `Ref_Key` из ошибки. Ручной `Number` не принимается.

12.09.2026 проверены HTTP 409 при нескольких договорах и HTTP 200 для preview с выбранным договором: итог 12 200, НДС 2 200. Выполнен один реальный запрос создания из текста, документ прочитан после `Post()`:

```json
{
  "Number": "ИНБП-000857",
  "Date": "2026-09-12T15:51:27",
  "Сумма": 12200,
  "Posted": true,
  "Ref_Key": "ac1d20d0-aea8-11f1-9f8b-fa163eced14c"
}
```

Ответы сохранены в `tmp/invoice-from-text-preview.json` и `tmp/invoice-from-text-create-result.json`; логи текущего сервиса — `tmp/server-text.stdout.log` и `tmp/server-text.stderr.log`.

При этой проверке `/ping` дважды вернул тайм-аут чтения корня OData (30 секунд); запросы справочников, предпросмотр, создание, проведение и чтение счёта завершились успешно. Реализация `/ping` не менялась.

## Создание с подтверждением

Для сценария с подтверждением сначала вызовите `/invoice-confirmation-preview` с тем же форматом текста, что у `/invoice-preview-from-text`. Можно добавить `clientRef`, `productRef`, `contractRef` для выбора из нескольких совпадений. При ошибке или неоднозначности возвращаются прежние 400/404/409/422; ID не выдаётся и документ не создаётся.

Успешный ответ содержит клиента (`client`), товар (`product`), договор (`contract`), количество, цену, ставку и сумму НДС, итог, `created: false`, уникальный `confirmationId` и `expiresAt` в UTC. Срок действия — **10 минут с момента подготовки предпросмотра**.

```powershell
$textInvoice = [System.IO.File]::ReadAllBytes('C:\1c-chat-api\examples\invoice-from-text.json')
$preview = Invoke-RestMethod http://127.0.0.1:3001/invoice-confirmation-preview -Method Post -ContentType 'application/json; charset=utf-8' -Body $textInvoice
$preview | ConvertTo-Json -Depth 6
```

После проверки показанных реквизитов отдельный запрос действительно создаёт и проводит счёт:

```powershell
$confirmation = @{ confirmationId = $preview.confirmationId } | ConvertTo-Json
Invoke-RestMethod http://127.0.0.1:3001/invoice-confirm -Method Post -ContentType 'application/json' -Body $confirmation
```

`/invoice-confirm` принимает только `confirmationId`; подмена цены, текста, номера или других реквизитов отклоняется HTTP 400. В памяти хранится отдельная копия документа из предпросмотра, включая дату, выбранные ссылки и расчёт. Она передаётся общему сервису создания без повторного разбора текста или пересчёта по новым настройкам. `Number` не передаётся, `Posted` сначала `false`, затем вызывается `Post()` и документ читается обратно.

Первое успешное подтверждение возвращает HTTP 201 и `{ Number, Date, Сумма, Posted, Ref_Key }`. Повтор с тем же ID до истечения срока возвращает HTTP 200 с сохранённым результатом без обращений к 1С. Одновременный запрос, пока первая попытка выполняется, получает HTTP 409. Ошибка создания или проведения блокирует повторную запись тем же ID: повтор получает HTTP 409 с доступными сведениями о результате, включая `Ref_Key`, если он получен. После тайм-аута нужно проверить 1С, прежде чем запрашивать новый предпросмотр.

Истёкшее подтверждение отклоняется HTTP 410. Неизвестный или уже удалённый ID получает HTTP 404. Очистка памяти выполняется раз в минуту и при подготовке нового preview. Если операция уже началась до истечения 10 минут, она завершается; очистка не снимает блокировку выполняющегося запроса.

Подтверждения и результаты хранятся только в памяти одного процесса сервера. Перезапуск удаляет их; старый ID больше не создаст документ. Каждый новый preview выдаёт независимый ID, даже для одинакового текста: защита от дублей действует в пределах одного `confirmationId`. Для этого режима все запросы должны попадать в один экземпляр сервера.

Этот сценарий добавлен отдельными маршрутами. Ранее существовавшие `/create-invoice`, `/invoice-create-from-text` и `/test-create-invoice` сохраняют свои правила прямого создания. Клиентский интерфейс, которому требуется подтверждение, должен использовать `/invoice-confirmation-preview` → `/invoice-confirm`.

Срок действия, неизменность сохранённых реквизитов, конкурирующие запросы, повторы после успеха/ошибки и отсутствие записи при preview покрыты локальными тестами с имитацией 1С.

## Боевой тест

`/test-create-invoice` использует фиксированные данные: «ТОРГОВЫЕ РЕШЕНИЯ ООО», договор покупателя «Основной договор» из ИНБП-000855, товар «Фискальный накопитель на 15 месяцев», количество 1, цена 12 200 с включённым НДС 22%. Контрагент, принадлежность договора и товар проверяются запросами к 1С. Тело запроса допускает только `dryRun`.

```powershell
# Только проверка реквизитов и расчёт:
Invoke-RestMethod http://127.0.0.1:3001/test-create-invoice -Method Post -ContentType 'application/json' -Body '{"dryRun":true}'

# Реальный тест; dryRun=false также действует для пустого объекта {}:
Invoke-RestMethod http://127.0.0.1:3001/test-create-invoice -Method Post -ContentType 'application/json' -Body '{"dryRun":false}'
```

Для этого endpoint журнал `tmp/test-invoice-state.json` предотвращает повторное создание, в том числе после перезапуска. После успешного теста последующие вызовы читают тот же документ из 1С. Незавершённый тест блокирует новый счёт ответом HTTP 409; журнал содержит уникальный комментарий теста и, если получен, `Ref_Key`. Не удаляйте журнал для обычного повторного запроса. Защита относится к отдельному тестовому endpoint; обычный `/create-invoice` создаёт новый счёт при каждом вызове с `dryRun: false`.

Боевой тест выполнен 12.09.2026. 1С назначила номер, документ проведён через `Post()` и прочитан обратно:

```json
{
  "Number": "ИНБП-000856",
  "Date": "2026-09-12T15:41:52",
  "Сумма": 12200,
  "Posted": true,
  "Ref_Key": "563e8f42-aea7-11f1-9f8b-fa163eced14c"
}
```

Результат записан в `tmp/test-create-invoice-result.json`. Логи запущенного сервиса — `tmp/server-test.stdout.log` и `tmp/server-test.stderr.log`. В логах отмечены найденные клиент, договор, товар, создание документа и подтверждённое проведение.

Сервис отправляет `Document_СчетНаОплатуПокупателю` с `Posted: false`, без `Number`. В табличной части используются реальные поля этой базы `Номенклатура` и `Номенклатура_Type`. Затем вызывает `.../Post()` и читает документ, возвращая номер, дату, сумму и фактический `Posted` из 1С.

## Ошибки и проверка

HTTP 400 — входные данные; 404 — объект не найден; 409 — неоднозначный поиск; 422 — несогласованные реквизиты; 502 — ошибка 1С; 504 — тайм-аут. `/ping` сохраняет прежний HTTP 500 при ошибке подключения. Ответы ошибок содержат понятное сообщение OData, а при наличии — код 1С и этап операции. Логи содержат идентификатор HTTP-запроса, запросы OData, длительность и результаты расчёта/проведения.

Создание и проведение — два отдельных запроса. Если проведение не подтверждено, ошибка содержит `details.created: true`, `Ref_Key`, `posted: null`, `retrySafe: false`. Документ нужно проверить в 1С по ссылке. После тайм-аута создания результат может быть неизвестен (`created: "unknown"`). Автоматических повторов записи нет; повторный `/create-invoice` может создать ещё один счёт.

```powershell
npm.cmd test   # Локальные тесты с имитацией 1С, без обращения к рабочей базе
npm.cmd run check   # Реальные ping, поиск клиента/товаров/договоров и предпросмотр
```

`check` использует пример этой базы и не создаёт документов. Для другого адреса сервиса задайте `API_URL`. На 12.09.2026 реальные проверки дали HTTP 200, найден «ТОРГОВЫЕ РЕШЕНИЯ ООО» (ИНН 2310213179), предпросмотр вернул итог 12 200 и НДС 2 200. Пройдены все 44 локальных теста; результаты предыдущих реальных проверок создания приведены выше.

Особенности протокола сверены с [документацией 1С Fresh](https://1cfresh.com/articles/data_odata); поля — с `$metadata` подключённой базы и существующим счётом ИНБП-000855. Для фильтров применяется кодирование пробелов `%20`, поскольку стандартное кодирование axios через `+` приводило в этой базе к неверным результатам и ошибкам запросов.
